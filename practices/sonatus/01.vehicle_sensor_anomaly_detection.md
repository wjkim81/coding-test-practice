## 첫 문제: Vehicle Sensor Anomaly Detection

### [Setting]
현대차 양산 차량들이 매초 다양한 sensor data(engine temperature, battery voltage, tire pressure 등)를 Sonatus Collector AI로 보내고 있어. 너는 가장 기본 building block 하나를 짜야 해 — **단일 sensor stream에서 anomaly를 감지하는 함수**.

### [Problem]
하나의 sensor (예: `engine_temperature`)에 대한 시계열 readings가 주어졌을 때, **anomaly point들의 index를 반환**하는 함수를 작성해줘.

```python
def detect_anomalies(readings: list[float], window_size: int = 10) -> list[int]:
    """
    Returns indices of anomalous readings.
    """
    pass
```

예시:
```python
readings = [85.0, 85.2, 85.1, 84.9, 85.0, 85.3, 85.1, 84.8, 85.0, 85.2, 
            85.1, 130.5,  # ← anomaly
            85.0, 85.2]
# Expected: [11] (or similar)
```

### [Constraints]
- Sliding window 기반 접근 권장 (단순 global mean 말고)
- `readings` 길이는 수천 ~ 수만 정도라고 가정
- "Anomaly의 정의"는 네가 정해도 됨 — 단, **왜 그렇게 정의했는지** 설명해줘

## 🟢 잘한 점 (3가지)

### 1. **Clarifying question을 정확한 타이밍에 던졌어** (사고 과정)
바로 코드 안 짜고:
- "streaming인가 batch인가?"
- "window_size는 왜 있나?"
- "첫/마지막 어떻게 처리?"

이거 시니어 면접에서 **가장 중요한 신호**야. 주니어는 문제 받자마자 코딩 시작하거든. 시니어는 "내가 뭘 풀고 있는지" 먼저 정의해. 특히 "window_size 왜 있어?"는 면접관 입장에서 *"이 사람 단순 정답 찾는 게 아니라 설계 의도를 묻고 있구나"* 신호로 읽혀.

### 2. **자기 경험에서 사고 transfer** (사고 과정)
- "CNN padding처럼 0 index 이전에 padding 하는 것도 한 방법?"
- "Real time까지 생각하면 과거로 보는 거밖에 없잖아?"

전자는 **다른 도메인 지식 끌어와 비교**, 후자는 **요구사항 추론 + 미래 호환성**. 둘 다 시니어 사고. 의료 imaging 경험을 차량 데이터에 자연스럽게 연결한 거, 이거 면접관이 보고 싶어하는 거야. "도메인 처음이라 못 함" vs "도메인 처음이지만 transfer 가능한 사고 보유" — 이 둘은 천지 차이.

### 3. **모르는 거 솔직, 그러나 reasoning은 멈추지 않음** (communication)
"robust statistics 처음 들어보는데... 그래도 통계로 안 되면 다른 방식 정의해야 되는 거 아닐까?" 

이게 시니어 답변의 정석이야. **모름을 솔직히 + 그래도 first-principles로 reasoning 계속**. 주니어는 "모르겠어요"에서 멈추고, 시니어는 그 뒤를 채워. 너는 후자.

## 🟡 개선할 점 (3가지)

### 1. **첫 구현에서 의도와 코드 사이 gap을 본인이 못 잡았어** (가장 중요)

우리 30분 동안 "window는 과거만, 현재 미포함" 합의해놓고, 코드는 **window 전체 안에서 anomaly 찾기**로 짰어. 우연히 결과가 비슷하게 나오니까 print 결과 보고 "됐다"로 넘어감.

**왜 이게 문제냐**:
- Production에서 가장 위험한 bug 패턴이야. "동작은 하는데 의도랑 다른 코드". Test pass하고 deploy 됐는데 edge case에서 깨짐.
- 면접관 입장에서 "이 사람 자기 코드를 자기가 검증할 수 있나?"가 의심돼.

**의식할 것**: 코드 짜기 전에 **한 줄로 의도 적기**.
```python
# For each i >= window_size:
#   compare readings[i] against statistics of readings[i-w:i]
```
주석 한 줄. 이게 있으면 코드가 그 의도랑 맞는지 손쉽게 verify 돼.

### 2. **Debugging print 의존 → dry run 부재** (whiteboard 면접 핵심)

너 스스로도 "whiteboard에서 print 박으면 안 되잖아" 짚었어. 맞아. 근데 진짜 문제는 print 자체보다 **"내 코드를 머릿속에서 실행 못해서 print에 의존"** 이야.

**의식할 것**: 코드 한 chunk 짤 때마다, 면접관에게 들리도록:
> "이제 i=11일 때 추적해볼게요. window는 [1:11], mean은 대략 85, std는 대략 0.16. readings[11]=130.5니까 difference는 45, k*std는 0.32. 잡혀요."

이거 30초도 안 걸려. 그리고 면접관에게 **"이 사람 머릿속에 코드가 돈다"** 강력한 신호. Print 박는 거랑 비교 안 되게 점수 높아.

### 3. **Production scale 질문에서 "기술적 답"만 함** (Sonatus 특화)

너는 "rolling sum 유지하면 streaming 가능" 답했어. 맞아, 기술적으로. 근데 **Sonatus 자리는 customer engineering**이야. 면접관이 "production scale은?" 물을 때 보고 싶은 건:

- 기술 답 (60%): 너 한 거
- **Business/customer 답 (40%): 못 한 거**
  - "현대차 OEM이라면 ECU 메모리 제약 확인 필요"
  - "Bandwidth cost 때문에 edge에서 1차 filter"
  - "Threshold가 차종별로 다를 거니까 config 시스템 협의 필요"
  - "False positive 한 번 터지면 dealer service center에 false alert 폭주 → 비용"

내가 마지막에 "edge vs cloud", "threshold 계층화" 얘기 채워줬는데, **그거 면접에서는 네 입에서 나와야 해**. 한국 OEM 자리는 특히 "이 사람 OEM이랑 협업해서 같이 문제 정의할 수 있나?"를 봐. 

**의식할 것**: "scale" 질문 들으면 두 갈래로 답하기:
1. 기술 (compute, memory, latency)
2. 운영 (cost, customer impact, config flexibility, deployment workflow)
