## 문제 2: Smart Sampling for Vehicle Data Collection

### [Setting]
Sonatus Collector AI는 차량들로부터 데이터를 수집해서 AI 모델 학습에 써. 근데 현실 문제:
- 차량 600만 대가 매일 어마어마한 sensor data 생성 → 다 cloud로 못 보냄 (bandwidth, storage 비용)
- OEM (현대차)이 "다음 ADAS 모델 학습용으로 lane change 상황 데이터 모아주세요" 요청
- 차량에서 1차로 filter해서 의미 있는 event만 cloud로 올려야 함

### [Problem]
하루 동안 한 차량에서 candidate events가 N개 발생했어 (예: 차선 변경으로 의심되는 순간들). 각 event는 다음 정보를 가짐:

```python
event = {
    "event_id": str,
    "timestamp": float,           # Unix timestamp
    "confidence": float,          # 0.0 ~ 1.0, "정말 lane change였을 확률"
    "scenario_features": dict,    # {"weather": "rainy", "speed": 95.0, "road_type": "highway", ...}
    "data_size_mb": float,        # 이 event 관련 raw data 크기 (10초간 camera + sensor)
}
```

이 중에서 **cloud로 upload할 K개**를 골라야 해.

```python
def select_events_to_upload(
    events: list[dict],
    bandwidth_budget_mb: float,  # 하루 upload 가능한 총 데이터량 (예: 500MB)
) -> list[str]:
    """
    Return list of event_ids to upload.
    """
    pass
```

### [Constraints]
- 총 upload data ≤ bandwidth_budget_mb
- 가능한 한 **모델 학습에 가치 있는** event들을 골라야 함
- N은 하루에 차량당 100~1000개 수준
- Edge에서 실행됨 (차량 ECU, 메모리 제약 있음)

## 🟢 잘한 점 (3가지)

### 1. **Framing 잡는 능력이 1차 mock 대비 확연히 좋아졌어**
> "아 다시 학습용으로 보내는 거구나!!"

이 한 마디가 senior급. 첫 문제 때는 *"window가 왜 있지?"* 같은 detail 질문이었는데, 이번엔 **문제의 framing 자체를 다시 잡았어**. *"이게 production inference가 아니라 training data collection이구나"* — 이거 못 잡으면 confidence 높은 거만 골라서 fail. 잡았으니까 전체 design 방향 자체가 바뀜.

이게 **시니어/스태프급 핵심 차이**야. Junior는 문제 풀고, Senior는 문제를 다시 정의해. 너 이번에 후자 했어.

### 2. **본인 도메인을 통해 cross-domain reasoning**
> "Lung cancer 1%인데 50:50으로 학습시키면 FP 늘 텐데 그래도 OK?"

너 의료 imaging 경험을 **자동차 문제에 적용해서 trade-off 사고**. 이게 면접관에게 *"이 사람 도메인 한정된 사람 아니다"* 신호 강하게 줘. 

Sonatus 자리 본질이 *"의료 같은 안전 critical AI를 자동차에 transfer"* 라서 이런 사고 패턴 보여주는 게 직접적 가치 입증이야. 본인이 "자동차 처음이라 약함"으로 framing 안 하고 "의료에서 본 같은 game"으로 framing 한 거.

### 3. **메타인지 — 면접 dynamics 자체를 의식**
> "그럼 면접관과도 이야기하면서 대략적으로 이런 문제는 의식하지만, 여기서는 시간 관계상 단순화할게요 라고 하면 되는 거지?"

이 깨달음. 솔직히 오늘 mock의 가장 큰 수확이야. 실력보다 *presentation*이 부족한 부분 — 너가 직접 발견했어. 이거 의식하고 면접 들어가면 다음 mock에서 큰 차이 날 거야.

## 🟡 개선할 점 (2가지)

### 1. **여전히 dry run 부재 → 같은 bug 패턴 반복**

오늘 두 문제에서 비슷한 bug 패턴이 반복됐어:
- **첫 문제**: 의도("과거 window로 현재 판단") ≠ 코드(window 전체 검사)
- **두 번째 문제**: 의도("greedy fill") ≠ 코드(`collected_mb` 업데이트 빠짐), 의도("remaining 중에서") ≠ 코드(전체에서 다시 뽑음)

너 본인도 *"bug는 계속 보이지만"* 인정했지. 이게 핵심이야. 코드 짠 다음 **20초 dry run** 한 번이면 위 bug 다 잡혀. `events_sorted` 첫 1-2개만 머릿속에서 따라가도:
> "events_sorted[0] = e1, data_size=100. uncertain_budget=100. 조건: 0 + 100 < 100 → False. 음? 안 들어가네?"
> "...아 `<=` 여야 하나? 그리고 `uncertain_collected_mb` 업데이트는?"

이게 1차 mock 때도 짚은 거랑 같은 패턴이야. **연습으로 충분히 교정 가능한 부분**인데 안 하면 면접에서 그대로 깨져. 

**실행 가능한 한 가지 규칙**: 코드 짠 다음 **"toy input 하나로 첫 2-3 iteration 머릿속에서 돌려본 후 면접관에게 설명"**. 이걸 강제 습관으로. 

### 2. **호기심 시간 관리**

첫 문제에서 design 단계 길었던 거 짚었는데 두 번째에서도 비슷. *"threshold 어떻게 정해?"*, *"random vs diversity?"*, *"scenario_features 같은 schema?"*, *"sort edge에서 돼?"* — 다 좋은 질문인데 각각 5분씩 들어가면 30분 끝남.

너 본인이 마지막에 이거 의식했고 *"명시하고 simplify"* 패턴까지 잡았으니까 다음 mock에서 의식적으로 *"호기심 잠시 봉인 → 코딩 진입"* 신호 만들어봐. 

**Phrasing**: *"이거 더 깊이 들어가고 싶은데, 일단 X 가정으로 코드 짤게요. 코드 끝나고 시간 남으면 돌아옵시다."* 

이 한 줄이 *"호기심 + 시간 의식 + 자신감"* 다 보여줘.
